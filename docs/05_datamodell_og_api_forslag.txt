# 05 — Datamodell og API-forslag

Prosjekt: Fordelsklubben / Flyttefordel MVP
Dokumenttype: PRD-del 05
Tema: Datamodell og API-forslag


## 1. Formål

Dette dokumentet beskriver en implementasjonsvennlig datamodell og API-struktur for app og admin. Det er ikke låst til ett konkret rammeverk, men er skrevet slik at Claude Code kan bruke det som grunnlag for å lage database, typer, API-ruter og service-lag.

Anbefalt retning:

- Relasjonsdatabase, f.eks. PostgreSQL
- TypeScript types/interfaces
- API-ruter med tydelig validering
- Soft delete på viktige entiteter
- Auditfelter på adminstyrt innhold

## 4. API-forslag for app

Base: /api

### GET /api/app/bootstrap

Returnerer grunnleggende data for appstart.

Response:

- user/session summary
- categories
- active heroes
- featured benefits
- pwa config


### GET /api/benefits

Query params:

- category
- postcode
- movingStatus
- featured
- nearby
- limit
- offset

Returnerer liste med aktive fordeler basert på målgruppe og periode.


### GET /api/benefits/:id

Returnerer detaljert fordel.

Må inkludere:

- advertiser
- category
- redemption config, men ikke nødvendigvis skjult unik kode før tildeling
- terms
- saved state
- user interaction state


### POST /api/benefits/:id/save

Lagrer fordel for bruker/session.

Body:

- userId optional
- sessionId


### DELETE /api/benefits/:id/save

Fjerner lagring.


### POST /api/benefits/:id/reveal-code

For generic_code:

- logger code_revealed
- returnerer kode

For unique_code:

- bør redirectes til assign-code endpoint eller håndtere samme logikk


### POST /api/benefits/:id/assign-code

Tildeler unik kode atomisk.

Body:

- userId optional
- sessionId

Response:

- code
- expiresAt optional
- alreadyAssigned boolean

Feil:

- CODE_POOL_EMPTY
- BENEFIT_NOT_ACTIVE
- NOT_ELIGIBLE


### POST /api/benefits/:id/copy-code-event

Logger at kode ble kopiert.


### POST /api/benefits/:id/qr-opened

Logger QR-visning.


### POST /api/benefits/:id/external-click

Logger ekstern lenkeklikk og returnerer URL eller redirecter.


### POST /api/leads

Sender lead.

Body:

- benefitId
- formData
- consentAccepted
- consentText
- sessionId/userId

Validering:

- benefit må være aktiv
- lead form må finnes
- påkrevde felter må være fylt ut
- samtykke må være akseptert hvis påkrevd


### POST /api/profile/postcode

Lagrer postnummer på bruker/session.


### POST /api/profile/moving-status

Lagrer flyttestatus.


### GET /api/saved-benefits

Returnerer lagrede fordeler.

## 6. Targetinglogikk

En fordel er synlig hvis:

1. status = active
2. nå er mellom starts_at og ends_at, dersom disse finnes
3. bruker matcher targeting_rules, eller fordelen applies_nationally = true
4. fordelen ikke er deleted/archived/paused

Targetingprioritet:

1. Eksakt postnummer
2. Postnummerområde
3. Kommune
4. Fylke
5. Flyttestatus
6. Nasjonal fallback

Hvis ingen fordeler matcher:

- returner nasjonale fordeler
- returner fallback hero


## 7. Sortering

Standard sortering:

1. Prioritet høyest først
2. Segmentmatch foran generell
3. Tidsbegrenset foran ikke tidsbegrenset, hvis relevant
4. Nyeste publisering

Admin skal kunne sette priority manuelt.


## 8. Excel/CSV-opplasting av postnummer

Admin bør kunne laste opp liste med postnummer for en fordel.

MVP-støtte:

- CSV med én kolonne: postcode
- Eventuelt Excel hvis enkelt å støtte
- Systemet validerer at postnummer er fire siffer
- Dedupliserer listen
- Lagrer i targeting_rules.postcodes eller egen benefit_postcodes-tabell

Ved mange postnummer anbefales egen tabell:

benefit_postcodes:

- id
- benefit_id
- postcode
- created_at

## 10. Sikkerhet

- Admin-endepunkter må kreve auth
- Rollebasert tilgang bør være enkel, men eksistere
- Input må valideres
- Leaddata må behandles som persondata
- Ikke eksponer skjulte koder før bruker faktisk ber om å hente/vise kode
- Rate limit på leadinnsending og kodehenting
- Audit log på publisering, sletting og eksport


## 11. PWA-teknisk

- manifest.json
- service worker eller framework-støttet PWA-oppsett
- app icons
- theme color
- offline fallback
- cache-strategi for statiske assets

Ikke cache persondata ukritisk.

## 13. Akseptansekriterier for datamodell/API

- Det er mulig å opprette en nasjonal fordel og se den i appen.
- Det er mulig å opprette en fordel målrettet mot postnummer.
- Det er mulig å opprette en fordel målrettet mot nylig flyttet.
- Det er mulig å vise fallback-hero når ingen regler matcher.
- Det er mulig å hente en generell kode.
- Det er mulig å tildele unik kode uten dobbeltutdeling.
- Det er mulig å sende lead med samtykke.
- Det er mulig å eksportere lead uten å registrere annonsørens oppfølging.
- Det er mulig å arkivere/utløpe fordel.
